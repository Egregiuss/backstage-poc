1. Overview 
This document describes the full process of deploying a Backstage developer portal application to Google 
Kubernetes Engine (GKE) using a fully automated CI/CD pipeline powered by GitHub Actions. 
  
This is not a theoretical guide. Every step in this document was actually carried out, every error was actually 
encountered, and every fix was actually tested. That is what makes this guide different from most 
documentation you will find online. 
  
1.1 What We Built 
A pipeline that automatically deploys a Backstage application to Kubernetes every time code is pushed to the 
k8s branch on GitHub. The full flow is: 
  
Git Push (k8s branch) 
   | 
   v 
GitHub Actions runs (build + test + compile) 
   | 
   v 
Docker image built from source code 
   | 
   v 
Image pushed to Google Artifact Registry 
   | 
   v 
Kubernetes cluster updated with new image 
   | 
   v 
App live at public IP via LoadBalancer 
  
1.2 Memory Hook 
Remember the full journey with this: G → D → R → K → B 
•       G = GitHub (your code lives here) 
•       D = Docker (your app gets packaged into an image) 
•       R = Registry (Artifact Registry stores the image) 
•       K = Kubernetes (GKE runs the image) 
•       B = Browser (you access the live app here) 
  
1.3 Key Technologies 
Technology What It Does 
GCP (Google Cloud Platform) Cloud provider hosting the infrastructure 
GKE (Google Kubernetes Engine) Managed Kubernetes cluster service 
Artifact Registry Stores Docker images (like a warehouse) 
Kubernetes (K8s) Orchestrates and manages containers 
GitHub Actions Automates the CI/CD pipeline on every push 
Workload Identity Federation Secure auth between GitHub and GCP — no keys 
needed 
Docker Packages the app into a portable container image 
Backstage The developer portal application being deployed 
  
2. Prerequisites 
Before starting, make sure you have all of the following ready. Skipping any of these will cause failures later. 
2.1 Accounts and Access 
• A Google Cloud Platform account (console.cloud.google.com) 
• A GCP project already created with billing enabled 
• A GitHub account 
• A GitHub repository containing your Backstage application 
2.2 Tools 
• A code editor (VS Code recommended) 
• Git installed on your local machine 
• Access to GCP Cloud Shell (browser-based — no installation needed)

5. Phase 3 — Create Kubernetes Cluster 
5.1 Objective 
Provision the group of virtual machines (nodes) that will run your application. Think of the cluster as the 
factory — it contains the machines, and your app runs as a worker inside it. 
5.2 Command 
Option 1: Create a new cluster using the auto mode - This can take up to 10 minutes to 
complete. This always works 
# checking the start time with the command date ; 
date; 
# command to create a k8s cluster 
gcloud container clusters create-auto backstage-cluster --region $REGION 
# checking the end time with the command date ; 
date; 
 
# command to get credentials of the cluster 
gcloud container clusters get-credentials backstage-cluster --region  $REGION 
 
# verify the kubectl context is correctly set  
kubectl cluster-info 
  
Option 2  
For this region, you can have a different region based on what you picked previously, eg (us -east1, us-west1) 
gcloud container clusters create backstage-cluster \ 
  --region $REGION \ 
  --num-nodes 2 \ 
  --disk-type pd-standard \ 
  --disk-size 50 
  
5.3 Validate 
gcloud container clusters list 
You should see STATUS: RUNNING in the output. 
  
5.4 Errors Encountered and Fixes 
  
Error 1 — SSD_TOTAL_GB Quota Exceeded 
GCP free/new accounts have a 500GB SSD limit per region. The default cluster uses 100GB SSD per node. 
With 6 nodes this exceeds the limit.  Fix: Use --disk-type pd-standard (HDD) and --disk-size 50 to stay 
within quota. Also switch to a different region (us-east1) if quota is exhausted in your original region 
(us-west1). 
  
Error 2 — Already Exists (code 409) 
If you press Ctrl+C during cluster creation, the cluster name gets registered even though creation failed. 
Running create again gives a 409 Already Exists error.  Fix: Delete the broken cluster first, wait for full 
deletion, then recreate.  gcloud container clusters delete backstage-cluster --region us-east1 
  
Error 3 — Cannot Delete While Provisioning 
If the cluster is in PROVISIONING status, GCP will not allow deletion. You get a 400 incompatible 
operation error. Fix: Wait for the cluster to finish provisioning (check with gcloud container clusters list), 
then delete. 
Warning — Ctrl+C 
Never press Ctrl+C during cluster creation or deletion. These operations take 3-5 minutes. Just wait. 
Interrupting them leaves resources in a broken state that is difficult to clean up. 
6. Phase 4 — Kubernetes Configuration Files 
6.1 Objective 
Define how your application runs inside Kubernetes. Three files are required, stored in a k8s/ folder at the root 
of your repository. 
Memory trick — DNS: 
• D = Deployment (tells Kubernetes how to run your app) 
• N = Namespace (isolates your app from other things in the cluster) 
• S = Service (exposes your app with a public IP) 
6.2 File Structure 
your-repo/ 
k8s/ 
namespace.yaml 
deployment.yaml 
service.yaml 
6.3 namespace.yaml 
apiVersion: v1 
kind: Namespace 
metadata: 
name: backstage 
 
6.4 deployment.yaml 
 
apiVersion: apps/v1 
kind: Deployment 
metadata: 
  name: backstage 
  namespace: backstage 
spec: 
  replicas: 1 
  selector: 
    matchLabels: 
      app: backstage 
  template: 
    metadata: 
      labels: 
        app: backstage 
    spec: 
      containers: 
        - name: backstage 
          image: nginx 
          ports: 
            - containerPort: 7007 
  
Note — nginx Placeholder 
The image: nginx is a placeholder. The real image gets injected by the CI/CD pipeline using kubectl set 
image on every deployment. You never need to manually update this value. 
  
6.5 service.yaml

  name: backstage 
  namespace: backstage

  type: LoadBalancer 
  selector: 
    app: backstage 
ports: - port: 80 
targetPort: 7007 
6.6 Errors Encountered and Fixes 
Error — Files Were Empty (0 bytes) 
The k8s/ folder existed on GitHub, but all three YAML files showed 0 bytes. This caused: error: no objects 
passed to apply. Cause: Files were created without content being saved inside them. Fix: Open each file 
in VS Code, paste the correct YAML content, press Ctrl+S to save, then git add k8s/ and git push. 
Error — Namespace Not Found During Apply 
When applying the whole k8s/ folder at once, Kubernetes sometimes tries to create the Deployment 
before the Namespace is ready. Fix: Apply files individually in order: namespace first, then deployment, 
then service. 
With this setup, when you push your code to GitHub or GitLab, the deployment will fail because some CI/CD 
dependencies need to be completed in GCP. 
7. Phase 5 — Artefact Registry 
7.1 Objective 
Create a private Docker image repository on GCP. This is where your CI/CD pipeline pushes the built image, 
and where Kubernetes pulls it from when deploying. 
Ensure your region and project ID values are set in the terminal session using this commands 
REGION=[the-region-where-your-cluster-is-created-in-i-recommend-europe-west2-if-close-to-europe] 
PROJECT_ID=[your-project-id] 
E.g 
REGION=europe-west2 
PROJECT_ID=project-9b8c91d6-b01a-4731-a77 
7.2 Create the Repository 
gcloud artifacts repositories create backstage-ayo \ 
  --repository-format=docker \ 
  --location=$REGION \ 
  --project=$PROJECT_ID 
  --description="Docker repo for backstage" 
  
7.3 Give the Cluster Permission to Pull Images 
gcloud projects add-iam-policy-binding $PROJECT_ID \ 
  --member="serviceAccount:$PROJECT_NUMBER-compute@developer.gserviceaccount.com" \ 
  --role="roles/artifactregistry.reader" 
  
Why This Is Required 
Kubernetes runs as a service account that has no permissions by default. Without explicitly granting 
artifactregistry. reader to the compute service account, pods will fail to start with an ImagePullBackOff 
error. 
  
7.4 Errors Encountered and Fixes 
Error — Underscores Not Allowed in Repository Names 
The original repo name backstage_ayo used an underscore. Artifact Registry only allows lowercase 
letters, numbers, and hyphens.  Fix: Use backstage-ayo (hyphen instead of underscore). Also update the 
REPO variable in your GitHub Actions YAML to match. 
  
 
  
8. Phase 6 — Workload Identity Federation 
8.1 Objective 
Set up secure authentication between GitHub Actions and GCP without storing any secret keys. This is the 
production-safe approach. 
Steps 
1. Create a service account 
2. Give permissions to the service account 
3. Create a Workload Identity Pool 
4. Create an OIDC GitHub Provider, aka A workload identity pool provider  
5. Add IAM policy bindings to the service account created in step 2 
  
8.2 Why Not Just Use a JSON Key? 
Comparison Detail 
Old method (JSON key) Modern method -Workload Identity Federation (WIF) 
Long-lived secret that never expires Temporary token that expires after each use 
Can leak if GitHub repo is compromised Nothing to leak — no key is ever stored 
Manual rotation required Fully automatic — no maintenance needed 
Not production safe Industry best practice 
 
8.3 Step 1 — Create a Service Account 
gcloud iam service-accounts create github-deployer 
  
SERVICE_ACCOUNT_EMAIL=github-deployer@$PROJECT_ID.iam.gserviceaccount.com 
  
echo $SERVICE_ACCOUNT_EMAIL 
  
8.4 Step 2 — Grant Permissions to the Service Account 
# Artifact Registry Admin 
gcloud projects add-iam-policy-binding $PROJECT_ID \ 
  --member="serviceAccount:$SERVICE_ACCOUNT_EMAIL" \ 
  --role="roles/artifactregistry.admin" 
  
# Kubernetes Engine Admin 
gcloud projects add-iam-policy-binding $PROJECT_ID \ 
  --member="serviceAccount:$SERVICE_ACCOUNT_EMAIL" \ 
  --role="roles/container.admin" 
  
# Storage Admin 
gcloud projects add-iam-policy-binding $PROJECT_ID \ 
  --member="serviceAccount:$SERVICE_ACCOUNT_EMAIL" \ 
  --role="roles/storage.admin" 
  
8.5 Step 3 — Create Workload Identity Pool 
gcloud iam workload-identity-pools create github-pool \ 
  --location="global" \ 
  --project=$PROJECT_ID 
  
POOL_ID=github-pool 
  
8.6 Step 4 — Create GitHub OIDC Provider 
Replace YOUR_GITHUB_USERNAME and YOUR_REPO_NAME with your actual values before running: 
  
gcloud iam workload-identity-pools providers create-oidc github-provider \ 
  --location="global" \ 
  --workload-identity-pool="github-pool" \ 
  --issuer-uri="https://token.actions.githubusercontent.com" \ 
  --attribute-mapping="google.subject=assertion.sub,attribute.repository=assertion.repository" \ 
  --attribute-condition="assertion.repository=='YOUR_GITHUB_USERNAME/YOUR_REPO_NAME'" 
  
POOL_PROVIDER=github-provider

9.4 Errors Encountered and Fixes 
Error 1 — YAML Indentation (uses: on wrong line) 
A common mistake is writing 'name' and 'uses' as two separate list items instead of one step.  WRONG: - 
name: Checkout Code - uses: actions/checkout@v4  CORRECT: - name: Checkout Code   uses: 
actions/checkout@v4  In YAML, indentation is everything. 'uses' must be indented under 'name', not a 
new list item. 
  
Error 2 — $GITHUB_SHA Not Resolving 
$GITHUB_SHA used in a shell run step sometimes does not resolve. Use ${{ github.sha }} instead — this is 
the correct GitHub Actions expression syntax. 
  
Error 3 — Artifact Registry Name with Underscore 
Artifact Registry repo names cannot contain underscores. backstage_ayo fails. Use backstage-ayo 
(hyphen). This must match in both the YAML env variable and the actual repository created in GCP.

10.4 Errors Encountered and Fixes 
 
Note: After the 1st successful deployment to k8s, the Backstage external service endpoint will not lauch 
the application until all the localhost entries in app-config.yaml and app-config.production.yaml are replaced 
with the  service’s external IP address 
To get the  service’s external IP address, run this kubectl command  
 
kubectl get service backstage -n backstage -o jsonpath='{.status.loadBalancer.ingress[0].ip}' 
 
Replacements  
 
Default After the change 
cors: origin: http://localhost:7007 cors: origin: http://34.105.132.25   
app: baseUrl: http://localhost:7007 app: baseUrl: http://34.105.132.25   
backend: baseUrl: http://localhost:7007 backend: baseUrl: http://34.105.132.25  
 
 
 
Error 1 — Database Connection Refused (port 5432) 
Backstage tried to connect to PostgreSQL on localhost:5432 but no database existed. This is because 
app-config.production.yaml had client: pg configured.  Fix: Change app-config.production.yaml to use 
SQLite in-memory for now:  database:   client: better-sqlite3   connection: ':memory:'  Note: This is a 
workaround. For production, a real PostgreSQL database should be provisioned. 
  
Error 2 — Content Security Policy Blocking eval() 
The browser console showed CSP blocking eval(), which prevented Backstage's frontend JavaScript from 
running.  Fix: Add script-src with unsafe-eval to the csp section in app-config.yaml:  csp:   connect-src: 
["'self'", 'http:', 'https:']   script-src: ["'self'", "'unsafe-eval'"]   img-src: ["'self'", 'data:'] 
  
Error 3 — White Blank Screen 
The Backstage frontend loaded but showed a completely white screen. This was caused by cors.origin in 
app-config.yaml still pointing to http://localhost:3000 instead of the real external IP.  Fix: Update 
cors.origin, app.baseUrl, and backend.baseUrl in both app-config.yaml and app-config.production.yaml 
to use the real external IP. 
Error 4 —Cached error messages 
The Backstage frontendis still not loading due to caching 
Solution: Try use another browser to test the url.

14.3 Key Principles Learned 
• Never store JSON service account keys in GitHub — use Workload Identity Federation 
• YAML indentation is critical — one wrong space breaks the entire pipeline 
• Real deployments always hit errors — reading error messages carefully is the skill 
• Kubernetes does not run your code directly — it runs Docker images 
• Cloud Shell loses variables on session reset — always re-export them when returning 
• GCP quota limits are real — use HDD disks and smaller sizes for learning projects
